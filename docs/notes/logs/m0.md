# M0 notes

- **Dead code:** `-O3` deletes work whose result is unused. `benchmark::DoNotOptimize(x)` keeps it.
- **First touch:** the first write to each page faults. Touch buffers during setup, outside the timed loop.
- **`leaks` vs ASan:** `leaks` finds heap memory nothing points to anymore. ASan catches bad accesses (out of bounds, use after free) when they happen.
- **RAII:** `std::vector` frees itself at end of scope. No `delete`.
- **Naive read bandwidth is 8.03 GiB/s, 5.6% of the 153 GB/s spec.** One `float sum` makes every add wait for the last one, so add latency sets the speed, not memory. The compiler won't split it into SIMD lanes: float addition isn't associative, so reordering changes the result.
- **Proof it's not memory:** 64 KiB (in L1) runs at 7.94 GiB/s, 1 GiB (RAM) at 7.81. Same speed from very different memory means the limit is the add chain.
- **4 sums → 27 GiB/s (3.4×), still the same in L1 and RAM.** The compiler packed `s0..s3` into one NEON register: the loop is `ldr q1` + one `fadd.4s` (4 float adds per instruction). Still one dependency chain, just 4 lanes wide. Legal because each lane keeps the order I wrote.
- **8 sums → 59 GiB/s L1, 56 GiB/s RAM.** Two `fadd.4s` chains (`v0`, `v1`) run in parallel, so speed doubled again. Speed ≈ chains × 4 lanes ÷ add latency. RAM is 6% behind L1: memory is starting to show.
- **16 sums (4 NEON chains): L1 96 GiB/s, RAM 64 GiB/s, and RAM stays at 64 with 32 or 64 sums.** That flat line is the single-thread memory ceiling: **~64 GiB/s (69 GB/s), 45% of spec.** Past it, more sums only help L1.
- **Don't trust the compiler to vectorize.** A `float s[16]` array became 16 scalar `fadd`s, not 4 vector ones, and ran no faster than 8 sums. Explicit intrinsics (`float32x4_t`, `vld1q_f32`, `vaddq_f32`) say exactly what runs.
- **Threads: 1 → 64, 2–4 → 76, 6 → 111, 10 → 121 GiB/s (129 GB/s, 84% of spec).** 2 to 4 threads hit the same wall (~76): likely the P-cluster's own limit. Adding E-core threads raises it, so the CPU's full bandwidth needs both clusters. That matters for PR-4 (P-core-only workers).
- **Google Benchmark sums each thread's wall time,** so multithreaded rates come out divided by the thread count. Check a new tool against a hand measurement before trusting it.
